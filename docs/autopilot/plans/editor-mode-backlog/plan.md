# Plan — 编辑器模式待办整理

> Track: `editor-mode-backlog`｜配套 `brief.md` 与 `checklist.md`。
> 本文件说明「清单是怎么整理出来的」以及「执行时的顺序与依赖」，不重复清单正文。

## 一、整理方法

1. **采集**：读取 S1–S6 六个来源（见 `brief.md` §二），逐条摘录待办陈述。
2. **去重**：把「运行时自动下载」在 S2、S5 两处的表述合并为一项；
   把「`@` 引用」与「资源管理器右键入口」按 S1 保持为两项（改动范围不同）。
3. **纠偏**：按 `brief.md` §三修正 S1 的过时结论；把 `gap-todo.md` 自身
   从「待办来源」降为「待更新文档」（P2）。
4. **补漏**：新增 S3/S4 两处改造后遗留的工程欠账（过时描述、失效的联调测试），
   这两项在原始 gap 分析里完全没有。
5. **排序**：P0 → P1 → P2 → P3 → P4；同级内按「改动小、收益明确」优先。
6. **标注**：每项给出「来源 / 改动范围 / Done when / Verify / 估时 / 依赖」。

## 三、依赖与推荐顺序

```
P2-1 修复联调测试 ──┐
P2-2 README 纠偏  ──┼── 先做（零风险、约 1 人日，把地基弄干净）
P2-3 gap 文档更新 ──┘
        ↓
P1-3 项目规则文件（1 人日，立刻见效）
P1-2 更多上下文入口（0.5–1 人日，纯增量）
P1-1 @ 引用（2–3 人日）
        ↓
P0-1 AI 改动 diff（3–5 人日）  ← 到这一步「选→问→改→看」闭环完整
        ↓
P2-4 Config schema（1–2 人日，为产品化铺路）
        ↓
P3-1 运行时自动下载（8–13 人日，装完即用的最后硬门槛）
        ↓
P3-2 同源反代（5–8 人日，需先解决 WS 动态路径）
        ↓
P3-3 Tab 补全（8–15 人日，需低延迟模型端点）
        ↓
P4-* 长尾
```

**关键依赖**：

- P3-1 之前建议先做 P2-4，否则自动下载的目录/端口/版本参数没有 schema 约束
- P3-3 与 P4-3（NES）共用同一套低延迟链路，NES 必须排在 Tab 补全之后
- P4-2（MCP）**不再是「打破边界」的问题**（Chat 本就是 Agent），
  但 DSH 已有 MCP 资源服务，优先级可一直压后

## 五、与项目 skill 的关系

`.dsh/skills/research-before-editor-feature/SKILL.md`（`alwaysApply`）要求：
**功能实现前先调研业内方案 → 出技术方案 → 交用户判断**。

因此这份清单里的每一项 P0–P4 在真正动手前，仍需按该 skill 走一遍调研与方案确认。
本 track 只负责「列出要做什么」，**不代替**单项的方案评审。
小型改动（P2-1/P2-2/P2-3 这类文档与测试修正）可由 AI 自行判断跳过调研。

## 六、不做的事（本 track）

- 不改产品代码、配置、测试
- 不删除 `docs/research/*` 原始调研记录
- 不替用户判断哪一项先做——优先级是建议，最终由用户拍板
